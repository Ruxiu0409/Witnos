## Development commands

Rust toolchain via rustup; make sure `~/.cargo/bin` is on PATH.

- `cargo test --workspace --exclude witnos-app` — the light loop: all tests (core unit tests, gate-CLI e2e matrix, the full-loop milestone test) without compiling the Tauri stack
- `cargo test --workspace` — everything incl. the GUI shell build (heavy: the tauri dependency tree needs several GB of target/ space)
- `cargo test -p witnos-cli --test full_loop` — the whole-v1-loop e2e only
- `cargo test -p witnos-core <name-filter>` — run a single test by name
- `cargo clippy --workspace --all-targets` — lint; keep it at zero warnings
- `cargo build --release -p witnos-cli` — produces the `witnos` bin at `target/release/witnos`
- `cargo run -p witnos-server --example serve` — run the core headless (binds an ephemeral 127.0.0.1 port, writes `$WITNOS_HOME/endpoint.json`, default `~/.witnos`; Ctrl-C = graceful stop, removes armed markers)
- GUI app (dev loop): `cd ui && npm install && npm run build` (frontendDist must exist before the Rust build — `cargo run` does not go through the tauri CLI, so nothing builds it for you), then `cargo run -p witnos-app`. **Terminals now need the bundled `witnos` bin** (they run in the PTY daemon): with no `witnos` in `target/` the app opens with no terminals and says so, so build the CLI first (`cargo build -p witnos-cli`) or point `WITNOS_CLI_BIN` at one
- **A bundle owns its own inputs (2026-07-30).** `tauri.conf.json`'s `beforeBuildCommand` builds the frontend, builds `witnos-cli`, and stages it into `crates/witnos-app/binaries/` (bundled at `Contents/Resources/bin/witnos`) — so a bare `tauri build` is correct on its own. It used to do none of that: only `scripts/install-app.sh` did, which meant `tauri build` run directly silently bundled whatever stale `ui/dist` and `binaries/witnos` were lying around. The hook's `cwd` is relative to `tauri.conf.json`'s own directory (verified empirically; the schema doesn't say). Known limit: the script is POSIX-only (`mkdir -p`/`cp`/`chmod`), so it needs a Windows arm before that platform can bundle.
- `scripts/install-app.sh` — one-shot release install: bundles `Witnos.app` via the tauri CLI (which now builds the frontend and the CLI itself, per above), replaces `/Applications/Witnos.app` (quitting a running instance), verifies the bundled CLI, and reopens the app (`--no-open` to skip). **The verification is `cmp` against the just-built bin, not an exec-bit check** — the old check ran the file, and build.rs's old empty-file placeholder runs as an empty shell script and *exits 0*, so "it executed" proved nothing.
- **Nothing may confuse a broken CLI for a working one.** build.rs still stages a placeholder so `cargo build/test -p witnos-app` works on a machine that never built the CLI (tauri-build validates bundle resources exist), but: the placeholder is a stub that **exits 1 with a message** rather than an empty file, and staging is keyed on "the staged bytes differ from the best real bin", not on `!exists()` — the latter froze the first answer forever, so one build made before the CLI existed left every later bundle shipping a broken CLI, undetected all the way to "the app opens with no terminals". At runtime the app resolves the CLI via `WITNOS_CLI_BIN` → exe-sibling → `Resources/bin/witnos`, and that resolution only tests `is_file()`, which is the reason the loudness has to live in the placeholder itself.

## What Witnos is

A local-first, open-source **thin layer** that sits on top of a user's existing coding agent (Claude Code, Codex, etc.). Its single job: make the agent's **verification step** ("did I actually do what was asked?") visible to the human and **editable by the human in real time, while the agent is still running**.

The problem it exists for: whenever there is room for the user's and the agent's understanding of **"how do we know it's done"** to differ, the agent verifies against its own standard and reports "done" — and that may not be what the user meant. This line does not coincide with subjective-vs-objective: even "does it build" leaves interpretation room (which environment, which version, must tests also pass). So the agent must not be the sole judge of its own completion; the human needs a place where that yardstick is visible and steerable. (Kin of the specification gap / oracle problem / Goodhart's law — made acute by long unattended runs.)

It is **not** an agent and does not replace the user's agent (BYOK — bring your own agent + credentials). It only makes the verification step of that agent transparent and human-interruptible.

The name comes from **witness** — every action the agent takes is watched under the user's eyes.

## The core loop (this IS the project; everything else is periphery)

Three roles: **User** (a capable engineer), **Agent** (the AI that writes code, e.g. Claude Code), **Tool** (this project — the layer between them).

1. User gives a goal.
2. Agent lays out "what I'll verify, how, and the result" onto the Tool.
3. Agent starts running.
4. User can add/edit a verification criterion at any time **without interrupting the Agent**.
5. On each check round, the Agent reads the **current latest version** of the verification content (this is the "living contract" — continuously re-read during execution, not a static doc read once up front).
6. If the Agent finds its work no longer matches the latest version, it **fixes the code first per its own understanding**, then lays back onto the Tool: "I interpreted your criterion as XXX, here's what I changed, here's the current evidence."
7. Next time the User looks, they judge whether the Agent got it right (**after-the-fact judgement** — the agent never stops to wait, so the human ruling happens later). The judgement is expressed as a change to the contract (edit the yardstick, or delete the item), not as a blessing: agreement is silence, and only disagreement needs an action — which then has to reach the agent, even if it has already stopped.

The value is **early interception** — catching a deviation before it compounds into the foundation of downstream work, at the lowest rework cost. The loop guarantees eventual convergence to "matches latest list"; the Tool's value is letting a human intervene *early*.

## Design principles (treat these as hard constraints)

These are the real content of the project. Any implementation decision must be checked against them.

1. **Evidence over intent.** Don't let the agent merely write what it *intends* to verify (intent can lie and can't be checked). Make it surface the **evidence it judged completion by** — screenshots it produced, the color-swatch list it detected, the contrast numbers it measured. Rationale: people are bad at proactively recalling unspoken expectations but good at being triggered by evidence in front of them. Turn the problem from "human must recall" into "evidence passively triggers."

2. **For subjective items, the human is the final judge (the Goodhart safeguard).** The tool guides the agent to decompose fuzzy standards into checkable proxy metrics, **but proxy metrics are only communication scaffolding, never the judge.** Objective items: the agent may self-check and self-pass. Subjective items: proxy metrics only carry evidence to the human; **the agent may never declare one passed.** (**Revised 2026-07-29**: the judge's lever is no longer a nod. An approve action existed and was removed — it changed nothing about the agent, because the release condition already treated "laid" and "approved" alike, and the user's honest default is that the agent's work is presumed right. So subjective items have no pass state at all: the terminal state is "evidence laid, and the human either changed the yardstick or didn't". The Goodhart line is unmoved — what is forbidden is the *agent* passing itself, and the human's levers are edit the item or delete it, each of which bumps the contract version and reaches the agent. **Revised again 2026-08-02**: send-back was a third lever and is gone too — it kept the criterion and argued with the evidence, but an edit already reopens the item, bumps the version, and staleness-marks the evidence, so re-saving even the same words says the same thing; and where the agent misread a criterion, writing it clearer beats telling it "again". Same test as approve: a lever whose only remaining difference is the agent's tone does not earn a domain state. Waiving went the same day, for the neighbouring reason: a criterion nobody checks does not belong in the contract, and a list full of tombstones is the reading load principle 4 exists to cut — so ✕ deletes, taking the item's evidence with it, and asks once first because nothing brings it back.) Never let subjective items auto-pass via proxy metrics — that is the Goodhart trap (the agent satisfies the numbers and produces something where every metric is right but the whole is wrong). This line must be held absolutely. A side door to guard: **the objective/subjective classification itself must not be the agent's call** — an item mislabeled objective silently bypasses the judge. Rule: **default subjective; an item counts as objective only if it carries a machine-executable oracle (a command + expected output)**; the human may explicitly promote an item to objective, taking responsibility for it. Classification errors must always fall toward "show the human more."

3. **Living contract, not upfront spec.** Do not depend on the user fully specifying requirements at the start — subjective/tacit things are inherently unspecifiable. The verification list stays editable and re-compared throughout the loop.

4. **Triage what surfaces.** More detail = more for the human to read. A 3-hour task may have hundreds of verifications; dumping all of them means the user reads none. The fix is **triage**: let the agent digest the safe items that need no human, and surface only the few that genuinely need human judgement. (The exact dimensions for "needs human judgement" are deliberately left undecided until real data exists.)

5. **The unit of control is a single goal; monitoring is opt-in per goal.** A project is a series of independently-issued goals (e.g. 20 of them). Within one goal's execution the agent runs to completion without stopping for the human. "Pay attention when I want to" is not a stop-gate inside one execution — it's simply: the user decides **per goal** whether to watch it and live-edit its verification. Watch goal 1–5, ignore 6–20, come back for the last 5 — each goal is an independent issuance, so "start watching the next one" is always available.

6. **After-the-fact judgement must be actively flagged, or it equals the agent deciding alone.** Since the human's ruling happens later, the tool is obligated to ensure the user doesn't miss the moment they should look — and, because the agent may already have stopped by then, to give the ruling a way back into the run (see "pushing a correction back into the agent's terminal" below; a verdict that can no longer reach the agent is a verdict about nothing). When the agent silently reinterprets a subjective criterion and lays it back, that must be **actively surfaced** (not buried among "passed" items) — otherwise the user only nominally holds judgement. This is the same mechanism as principle 4 (triage): the agent's new interpretation of a subjective item is exactly the kind of thing that should surface.

## Technical direction (planned)

- **Integration model: BYOK.** User brings their own coding agent and credentials. The tool never touches the user's tokens or proxies credentials. Reference architecture: local daemon + UI, scanning PATH for available agent CLIs, connecting via per-agent adapters (cf. Open Design / nexu-io/open-design). **The UI is shipped as a cross-platform desktop app, not a browser web page** — see "Stack decision (v1)" below.
  - **Do not** pursue "extract subscription login tokens and drive the agent yourself" — billing third-party agents against subscription quota is banned (2026/02) and OAuth tokens are fragile. The correct path is API key, or (for self-use) official Agent SDK credit.
- **Binding mechanism: thin layer on existing agent lifecycle hooks (Path A).** Do not build an agent runtime. The best prototype base is **Claude Code**:
  - **Stop hook** — fires when the agent thinks it's done; can return `block` to force it to continue until the release condition is met (see the central state machine in "Stack decision (v1)"). This is the core of "intercepting 'I'm done'."
  - **http hook** — can call an external service with an Authorization header, so the verification list and judgement logic live in this tool's own backend. **Caution: the http hook FAILS OPEN** (timeout / non-2xx / connection failure → the agent continues unblocked). Since the whole product *is* the block, **do not use the http hook as the Stop gate.** The gate must be a small **command-hook shim that FAILS CLOSED** (emits `{"decision":"block"}` whenever Witnos is unreachable while armed — see the arm/disarm protocol in "Stack decision (v1)").
  - **agent / prompt hook** — use a (sub-)model to make subjective-verification judgements.
  - (Codex currently only supports command hooks; prompt/agent hooks are parsed but skipped. Because hooks are converging toward a cross-tool standard, **the verification-list format must be designed agent-agnostic** to ease swapping the base later.)
- **The living contract needs two channels, not just Stop.** Stop fires when the agent thinks it's done — for a single goal that is often the very end; if mid-run edits all land at the finish line, that is end-stage interception, not early interception. So: **Stop hook = the gate** (on "I'm done", compare against the latest contract and release or block — release condition: the central state machine in "Stack decision (v1)"); **a high-frequency hook (PostToolUse) = the delivery channel** (after each tool call, a **purely local** version compare — contract unchanged: zero-cost silent pass; changed: fetch **only the changed items** from the core and inject them into the conversation). Both channels share one store and one `witnos-gate` bin (subcommands), but fail in opposite directions: **delivery fails OPEN** (can't fetch → skip silently; the gate still catches the final result), **the gate fails CLOSED**. Injected/block content is always a delta, never the full list — re-feeding hundreds of items every round makes the agent re-litigate passed items and burns tokens.
- **Evidence scope for v1:** ship **only "agent-curated evidence" (the agent reports what it verified, its conclusion, and its basis) plus collaborative editing** — that's the core loop. The "unfilterable raw trace" (full diff, commands run, outputs) is deferred to a conditional next step, and even then must not be a raw dump (would violate principle 4) — it must be triaged to a few glanceable items. Curated evidence must carry its own insufficiency sensor: every evidence item includes a **provenance pointer** (file path, command run, URL) with one-click open-the-original in the UI, and the tool logs "human drilled down, then changed a ruling or added an item" events — that log is the requirements spec for how the raw-trace layer should filter, and raw data for principle 4's triage dimensions. Evidence is also stamped with a **workspace fingerprint** (commit / dirty hash) at capture time; if the code moved afterwards, flag the evidence stale so the human never nods at an outdated screenshot.

## Stack decision (v1)

**Decided** (cross-platform desktop app, not a web page). Form factor and platform are settled; the rest below is the concrete v1 shape, chosen against the project's values (thin layer, fork-easily, fail-closed gate, agent-agnostic). There is still no code — these are the constraints implementation must honor.

- **Shell: Tauri 2** (native Rust core + OS webview), cross-platform (macOS + Windows + Linux). Native installable app, not a browser tab. Chosen over fully-native (Swift, macOS-only, loses TS reuse) and Electron/Node-sidecar (ships a JS runtime + hits Tauri's declined `externalBin` notarization bug).
- **Layout: one Cargo workspace, two Rust bin targets, one TS frontend.**
  1. **GUI core** (the Tauri app): on startup `tokio::spawn` an **axum** server bound to `127.0.0.1` on an **ephemeral port**; write `{port, token}` to `~/.witnos/endpoint.json` (mode `0600`). Serves `POST /gate` (+ the CRUD the gate needs).
  2. **`witnos-gate`** — a **separate GUI-free bin in the same workspace that does NOT depend on the `tauri` crate** (so it links no webview runtime: ~few-hundred-KB, ms start, headless/CI-safe). Serves **both hooks via subcommands: Stop (gate) and PostToolUse (delivery)** — see Technical direction. Gate flow: reads hook JSON on stdin → reads the armed marker (see the arm/disarm protocol below) and `endpoint.json` → POSTs to the core with the bearer token → **FAILS CLOSED while armed**: on *any* error (connection refused, timeout, non-2xx, malformed, missing endpoint file) it prints `{"decision":"block", ...}` and exits; **with no armed marker it allows** (this project isn't being watched). Keeping the load-bearing path one-language/one-repo is the point.
- **Frontend: TS SPA (React or Svelte) in the webview.** The reuse that actually applies from the cited references (nexu-io/open-design, OpenCoworkAI/open-codesign) is the **live-panel UI**, not their Node daemon. The daemon half is re-implemented in Rust — a **bounded translation** (one gate route + a JSON store + a PATH scan), not a redesign. This is the honest cost of going desktop-native.
- **Icons: Lucide paths inlined, not emoji and not SF Symbols (2026-07-30).** Emoji were holding the job and read as decoration rather than interface: own colours, own metrics, a different face on every OS — three things a dense tool UI has to control and emoji grant none of. SF Symbols fails twice over: its licence permits use only in the UI of software running on an Apple operating system (which excludes both a webview page and a cross-platform app), and the font does not exist on Windows/Linux, which the form-factor decision already committed to. Fourteen Lucide (ISC) paths live in `ui/src/Icon.tsx`, stroked with `currentColor` so an icon is simply whatever the text beside it is — `--dim`/`--accent`/`--bad` and both themes reach it for free — on one 24-unit grid that also matches the hand-rolled sidebar toggles already in the file. **Inlined rather than depending on `lucide-react`**: fourteen icons do not earn a dependency that someone forking this has to take on. Keys are Lucide's own names, so any of them can be looked up or swapped at lucide.dev. Deliberately left as text: real keyboard symbols (⌘ inside `<kbd>`) and Claude Code's own title marks (`·`/`✳`) — the latter are parsed data, not drawn icons.
- **Store: one serde-JSON file per goal behind an `RwLock`** (thinnest, most forkable, local-first single-user). Move to `rusqlite` only if real concurrent webview-edit + gate-read contention shows up. The GUI core and the gate hit the **same in-process store**, so what the human edits *is* what the gate reads each round — the "living contract" with no cross-process sync.
- **The central state machine: gate release ≠ item pass.** The agent never waits for the human — so the Stop release condition is "all objective items pass ∧ all subjective items have interpretation + evidence laid out ∧ reconciled against the latest contract version", **not** "everything passed"; "agent done, evidence laid for the human to look at" is a normal terminal state of a goal. **A criterion nobody wants checked is deleted, evidence and all** — the per-item half of principle 5's opt-in. Goals recorded before that replaced waiving still carry `Waived` items, and those are skipped before every clause of the condition: aliasing them onto `Open` would silently re-arm a check their owner had already opted out of.
- **The human's two levers both bump the version (2026-07-29; three became two on 2026-08-02).** Editing an item and deleting it each bump `contract_version` (an edit also stamps the item's `last_edited_version`), which is what makes them reach a *running* agent through the PostToolUse delivery channel instead of only surfacing when it next tries to stop. A status change that does not bump is invisible to that channel — that was the original defect behind "rejecting it did nothing"; that button is now gone entirely (`ItemStatus::Rejected`, `Store::reject_item`, `POST /goals/{id}/rulings` and the UI's ruling row with it), since edit does all of its work. Old stores still load: `rejected` serde-aliases to `open`, and `EventKind::Ruling` survives as a read-only historical variant because that event log is the core bet's readout. The anti-rubber-stamping flag (`after_drill_down`) moved onto `ContractEdited` — true only on the human's IPC path, false for agents and over HTTP. **Deletion has one trap waiving didn't, and it is closed:** a deleted row cannot appear in `items_since`, so the delivery channel also reads `Goal::deletions_since` — derived from `EventKind::ItemDeleted`, which is why that event carries the claim text and the version (afterwards the id names nothing). Without it a running agent keeps producing evidence for a criterion nobody holds and finds out only by hitting `ItemNotFound`. `ItemStatus::Waived` and `EventKind::Waiver` stay as read-only legacy, same as `Ruling`. The goal also carries `last_human_edit_version`, moved only by human actions: the agent bumps the version itself whenever it lays items, so "the version moved" cannot be used to mean "the human changed something" (the UI would nag through every ordinary run — principle 4).
- **The terminals outlive the app (2026-07-30, confirmed end-to-end).** A goal is bound to one session id and that id never comes back, so hanging up the shells on quit made a contract's lifetime one app run. `witnos pty-serve` owns them instead — tmux's one load-bearing trick without taking tmux as a dependency, in the headless bin that already may not depend on `tauri`. Protocol (full spec in that module's header): one socket, two kinds of connection — control carries newline-delimited JSON (open/list/resize/kill/**foreground**), and data is one connection per session carrying **raw bytes with no framing** after a single hello line, because an agent printing megabytes must not pay for base64 or per-chunk headers. Attach replays a bounded scrollback and continues live with no gap or duplication; that seam is structural, not timed. Session ids are monotonic across daemon restarts and never reused — an id is how a goal names its agent's terminal, so reissuing a live one would type a correction at the wrong agent.
  - Three consequences to keep: **unmount detaches, only ✕ and restart kill** (StrictMode mounts twice, and quitting must never kill — that is the whole feature); the app takes a **census at startup** and restores each surviving pane under its old id, opening a fresh one only if none survived; and the zombie accounting inverts — `account_ended_panes(surviving)` spares any goal that still owns a live pane, and **skips entirely when the census cannot be taken** ("I don't know" must never become "it ended"). Layering: the core takes the list, the app asks the daemon; a headless core has no terminal layer and no longer sweeps at all.
  - **A pane belongs to a project, and closing a goal opens the next shell (2026-07-30).** Once shells persist, a pane is a workspace — an agent, a transcript, a place in a directory — so selecting a project no longer walks the shell you were typing in over to it: it opens a pane there and leaves the old one standing, and clicking back focuses the pane already sitting in that project (or under it, if you cd'd down into a crate) rather than opening a second one. The `cd` walk survives only as the last resort for a stack with no room for another pane, where the choice is between moving a shell and the click meaning nothing. Closing a goal likewise **opens a fresh shell in its project**: a goal is bound to one session id and an id never comes back, so the next issuance needs a new session, and the workspace hands one over instead of leaving it as a step to remember — while the closed goal's own pane keeps running, because its scrollback is the record of the work just finished (✕ and restart stay the only things that kill). Both wait on the startup census: before it lands the app cannot tell "no shell is in that project" from "no shell is known yet", and would open a duplicate of a pane it is about to restore — the same "I don't know is not an answer" rule as the zombie accounting above.
  - **Known cost:** while the app is closed nobody is watching — a graceful quit removes the armed marker (so no stray stall), but a *crash* leaves it and the surviving agent stalls at its next Stop against a core that isn't there. Persistence turns that pairing from an edge case into a normal one. The natural end state is moving the axum core into the daemon so the GUI becomes a pure client — which is the README's own "local daemon + UI" reference architecture — deliberately deferred. Windows has no daemon (ConPTY offers neither a readable foreground process group nor a filesystem socket), so its terminals still die with the app.
- **Pushing a correction back into the agent's terminal (2026-07-29).** After-the-fact judgement is worthless against an agent that has already stopped, so a correction has to be able to start a new turn. The app owns the terminal the agent runs in, so it types the correction into that pane: each shell is stamped `WITNOS_PANE` (inherited by hooks the way `WITNOS_TERMINAL` is), the UserPromptSubmit hook records it on the session binding, and an IPC command resolves goal → session → pane and writes one line. **The safety guard is "does a foreground program own the pane"** — the inverse of the guard for typing `cd`, which needs a shell to run it; typing prose at a bare shell would execute it. Whether the agent is idle or mid-turn is *not* a safety question (keystrokes land in Claude Code's input box), only politeness: the UI reads Claude Code's own OSC title (`·` idle, `✳` working) and skips typing while it works, because the delivery channel already carries the change on its next tool call. The contract carries a monotonically increasing version number (mirrored into the armed marker so the delivery channel's "unchanged" check touches no network); every piece of evidence and every reconcile is stamped "against version N" — the trust basis of after-the-fact judgement is being able to prove the agent saw your edit. After a goal closes the list stays viewable, but the UI must say plainly: no agent reads this anymore — to change the outcome, re-issue the goal (principle 5's boundary).
- **Subjective-item judgement = Claude Code's own prompt/agent hook** (in `settings.json`), run by Claude Code with the **user's own credentials**. Witnos needs **zero in-process LLM glue** for v1 — so "no Anthropic Agent SDK in Rust" is irrelevant here. The Rust core only stores the agent's interpretation + evidence and actively flags reinterpretations (principle 6).
- **`witnos init`** installs into the **project-level** `.claude/settings.json` (not user-global — see the arm/disarm protocol below), four things: the Stop and PostToolUse command hooks (both → the bundled `witnos` bin, absolute path), the subjective-judgement prompt hook, plus a short **contract-authoring prompt** (each item = claim + how it's checked + what evidence to attach; subjective items must include the agent's interpretation; after laying out the initial contract the agent must run a **blindspot pass** — propose candidate items the user likely hasn't thought to verify, default-subjective, awaiting whatever the human does with them — edit or delete; **and the contract is written in the user's own language** — the prompt itself is English, which was enough to make an agent answer a Traditional Chinese goal with English claims and evidence, and evidence the human can't read triggers nothing, which is the whole mechanism of principle 1. The rule keys off the user's own prompts, not the app's UI language: the hook can't see the webview's setting, and the words being typed at the agent are the better signal anyway) — hooks can only force the agent to stop; good contracts come from the prompt side. **The app's "watch a project (auto)" runs `witnos init` for you** via the bundled CLI (shell-out keeps one implementation; `current_exe()` inside it IS the correct absolute hook path), then registers the dir and arms the marker. The folder-trust caveat is surfaced as a UI notice after adding.
- **Contract schema + agent write path (decided 2026-07-26, details in the local-only working doc `docs/schema-v1.md`):** Goal/Item/Evidence/Event fields, the formalized release condition, and the origin instrumentation (the strong-bet readout) live in that doc. The agent reads/writes the store via **subcommands of the same headless bin**, called through Bash — running a shell command is the lowest common denominator across coding agents; endpoint/token handling stays inside the bin so prompts never touch credentials. Bin naming resolved at the same time: **a single headless bin named `witnos`** (the `witnos-gate` role above becomes its `hook` subcommand family; the no-`tauri`-crate constraint is unchanged).
- **Distribution:** single signed `.app` / `.exe` on the OS webview (low-tens-of-MB, not Electron weight). For self-dogfooding, **run unsigned / ad-hoc** — macOS notarization + Windows signing are deferred until shipping to other machines and do not block v1 validation.
- **Fail-closed applies only while armed (arm/disarm protocol):** an unconditional "unreachable → block" would stall every Claude Code session in every project whenever the app isn't running. So: a watched project carries an **armed marker file** (`.witnos/armed.json`), removed on graceful stop; the gate blocks only when "marker present ∧ core unreachable". App crash leaves the marker → correct stall; projects not using Witnos → never harmed. The deliberate stall remains a known UX cost and must be surfaced: a visible "watching N goals" indicator, and **the block reason string is itself the escape-hatch documentation** ("Witnos unreachable — open the app, or run `witnos disarm`") — when stalled, the user's eyes are already on the transcript.
  - **Marker v2 (2026-07-29, auto mode):** `{v: 2, auto, default_goal?, sessions: {session_id → {goal_id, contract_version, agent_synced_version}}}` — the whole file is a **pure derivation** of (registry ∋ dir, that dir's goals in the store), written tmp+rename; only watching goals contribute; a session's own auto goal always wins its slot; the newest watching manual goal is `default_goal`. Legacy single-goal markers still parse (normalized to `default_goal`). **One goal per agent session**: hooks resolve their session's entry; the Stop gate for an unbound session in an auto project asks the core by `(project_dir, session_id)` — goal exists & watching → normal evaluation (+ marker heal); human opted the goal out → release (opt-out beats fail-closed, principle 5); genuinely unbound → block (core was down at every prompt — exactly the silent-failure window fail-closed exists for). **Scope narrowing (2026-07-29): owning a goal is what gets you gated.** A session with an entry is evaluated wherever it was started; a session with NO goal is stalled only when it carries the `WITNOS_TERMINAL` stamp — otherwise it is released, including when the core is unreachable or the marker is torn, because stalling a session that owns no contract protects nothing and lands in whatever terminal the user is actually working in. An auto project with zero goals KEEPS its marker and stalls its own terminal's sessions. Auto-mode registry = `~/.witnos/projects.json`, human-only surface (IPC, never HTTP); `witnos disarm` removes the marker but the registry re-arms on app restart (the message says so — remove the project in the app to stop for good).
  - **Agent-facing subcommands take `--goal <id>`** (required whenever several goals are active in one project): a Bash call carries no session identity, so goal identity travels in-context — the protocol injection, every delivery delta, and every block reason print it. Without the flag the CLI resolves only an unambiguous marker.
- **When to reconsider:** the first genuinely TS-shaped need (roadmap step 4 — adding Codex and wanting to lift an open-design adapter *verbatim*; or step 5's raw-trace shaping) justifies extracting a **TS sidecar supervised by the Rust core**. Do not pre-pay this for v1.
- **Implementation notes:** bind a "goal" to a Claude Code session via a UserPromptSubmit hook (it receives `session_id` and `prompt` — the latter verified empirically 2026-07-29, see the spike report); in auto mode that hook get-or-creates the session's goal (title = first prompt, whitespace-collapsed, 80-char cut; failure does NOT mark the session instructed → the next prompt retries, healing transient core outages; a goal the human opted out is returned unwatched and never re-watched); `/clear`/resume mean a new session id → a new goal (chosen semantics, not a bug); a **SessionEnd hook** (4th installed hook, verified on 2.1.220 — input carries `session_id`/`cwd`/`reason`) accounts a goal still `running` when its session ends as `turn_ended_unmet` (fail-open bookkeeping via `POST /goals/{id}/turn-ended`; only exact marker `sessions` entries qualify — a shared default goal is not flipped by one session ending; the gate firing again revives the goal to `running`); handle the `stop_hook_active` flag on Stop input, keeping "deliberate fail-closed stall" and "infinite block loop" semantically distinct; long tasks go through context compaction — on reconcile, have the agent re-read its own previous interpretations from the store rather than re-derive them.
- **Verified against the official hooks docs AND empirically on Claude Code 2.1.220 (2026-07-26; method, raw evidence, and a rerunnable harness in the local-only working doc `spike/hooks-2026-07-26/`):**
  - **Both delivery channels work, tested:** PostToolUse now DOES support `hookSpecificOutput.additionalContext` (contrary to the 2026-07-03 note; injected next to the tool result), and **exit code 2 + stderr** also works ("Shows stderr to Claude"; the tool already ran, so nothing gets blocked). Use additionalContext for delivery, keep stderr as fallback. Matcher `"*"`; command hooks default to a 600s timeout with a per-hook `timeout` override. (The previously-noted `continueOnBlock` is no longer documented — do not rely on it.)
  - **Stop `{"decision":"block","reason":…}` works, tested** — and the reason string actually steers the agent's next move. `stop_hook_active` is no longer documented but still present in the input (false on first block, true after); input also carries `last_assistant_message` and `transcript_path`; UserPromptSubmit input carries `session_id` **and `prompt` (the user's text — verified 2026-07-29 on the same 2.1.220, raw sample in the spike report)** — goal↔session binding and prompt-titled auto goals are both feasible.
  - **Consecutive Stop blocks cap out at 8, measured**: the 9th consecutive block's reason lands in the transcript but the turn ends right there (headless: empty stdout, no warning). The armed stall is therefore not infinite — account the goal as "turn ended, release condition unmet"; never assume a block can hold the agent forever.
  - **Fail-open confirmed empirically**: a crashing (exit 1) Stop or PostToolUse hook is silently ignored; the hook runner treats non-0/non-2 exits, timeouts, and hook crashes as continue — so fail-closed must be guaranteed inside `witnos-gate` itself: internal timeouts far below the hook timeout, and the panic handler must still print the block JSON.
  - The http-hook fail-open claim is doc-backed: "HTTP hooks can't signal a blocking error through status codes alone" — only a successful 2xx with proper JSON can block; unreachable/timeout/non-2xx all mean the agent continues.
  - **Trust prerequisite:** untrusted folders ignore `permissions.allow` in project settings (hooks still executed there in headless 2.1.220, but don't rely on it) — `witnos init` must account for "the folder must be trusted first".
  - The hook API still moves fast (30 documented events now, incl. new ones like PostToolUseFailure/StopFailure); prompt/agent-type hooks were NOT tested this round — retest with the same harness before v1 implementation.

## The core bet (most important)

> **Showing a human "evidence" lets them catch their own unspoken expectations better than showing them a "text checklist."**

If this is false, the tool is just a prettier checklist. When building/using the minimal prototype, watch specifically for the **strong version**: does the user actually catch things *not previously written in the list* **because they saw evidence** — not merely feel "the info is thorough." (Weak version "more evidence helps" is near-certain; the product bets on the strong version.)

Validation method chosen: build a minimal version and dogfood it — **instrumented, not vibes**: every contract add/edit records its provenance — (a) written before the run, (b) added while viewing a specific evidence item (record which), (c) spontaneous mid-run. The count of (b) is the direct readout of the strong version, and the same metric works for the fallback experiment; near-zero cost since edit events land in the store anyway. Cheap fallback if no resonance: Wizard-of-Oz — run a real task with an off-the-shelf agent, manually assemble its evidence, split a few engineers into two groups (one sees text-only list, one sees evidence), compare whether the latter catches more un-pre-written gaps.

## Scope and non-goals (current)

- **Local-first, single-user, open-source.** No cloud, no cross-user data collection.
- **No moat sought.** Being clean enough to understand and fork easily is a feature.
- **Does not replace the agent harness.** Only the "verification transparency + collaboration" layer.
- The tool is **domain-neutral**: it understands *process*, not *content*. It does not embed any domain's evidence extractor — "what evidence to surface" is produced by the Agent. Aesthetics, taste, and technical judgement (correctness, edge cases, codebase conventions, security) are all the same action to the tool: force the agent to surface evidence, let the domain authority poke at it.
- **Target user and value ceiling.** The user is someone whose judgement is already adequate but who is locked outside the agent's black box (typically a software engineer). The tool **does not make the user smarter** — it gives existing judgement a place to act. Its value ceiling is the user's own cognition: surfacing evidence to someone who lacks the relevant concept (e.g. "Apple uses only black/white/grey") does nothing. Don't design features premised on teaching the user the domain.
- **Explicitly out of scope (recorded only):** learning "what people usually miss for this kind of task" from de-identified cross-user data — conflicts directly with local-first / no-data-exfiltration positioning.

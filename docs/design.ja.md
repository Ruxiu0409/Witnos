# Witnos 設計ノート

> [プロダクト README に戻る](../README.ja.md) · [English](design.md) · [繁體中文](design.zh-Hant.md)

プロダクト README は意図的に短くしています。この文書には、Witnos の背景にある問題、設計制約、中心仮説、技術判断を残しています。

## なぜ必要なのか

エージェントはループを回します。**推論 → 行動 → 観察 → 繰り返し**。弱いのは「観察」の一歩です。

本当の問題は、目標が客観的か主観的かではありません。**「どうなったら完了なのか」について、あなたとエージェントの理解がずれうるかどうか**です。ずれる余地がある限り、エージェントは自分の基準で自己検証し、「完了」と報告し、別のものを渡してきます。

この線は主観／客観とは一致しません。主観的な目標に解釈の幅があるのは当然です——「Apple らしいアプリにして」の「Apple らしさ」は人によって違います。しかし**一見客観的な目標でも、検証方法そのものに曖昧さが残ります**。「ビルドが通るか」は硬い基準に聞こえますが、どの環境か、どのバージョンか、テストまで緑でなければ駄目なのか——「ビルドが通った」の定義自体に解釈の余地があります。重要なのは目標の性質ではなく、**検証方法についての理解が両者で一致しているか**です。

このギャップ自体は古い問題です（specification gap、oracle problem、Goodhart の法則はいずれも親戚です）。ただし**長時間の無人実行**がそれを深刻にします。人が見ていない状況で、最初の一歩で捕まらなかったズレが次の一歩の土台になり、静かに複利で積み上がる。エージェントが「完了」と言う頃には、曲がっているのは 1 つのファイルではなく意思決定の連鎖全体です。

**中心的な主張：「完了」が二通りに解釈されうる限り、エージェントが自分の完了を単独で判定してはならない。完了条件は人に見え、編集できなければならない。**

### ループ

登場人物は三者。**ユーザー**（判断力のあるエンジニア）、**エージェント**（実際にコードを書く AI）、**ツール**（このプロジェクト、両者の間の層）。

1. ユーザーが目標を与える。
2. エージェントが「何を・どう検証し・結果はどうか」をツールに並べる。
3. エージェントが走り出す。
4. ユーザーはいつでも項目を追加・修正できる——**エージェントを中断せずに**。
5. エージェントは各チェックのたびに**その時点で最新版**の契約を読む。これが「生きた」の意味です。実行前に一度読んで終わる死んだ文書ではなく、実行中に読み直され続ける。
6. 最新版と食い違っていると分かったら、エージェントは**まず自分の解釈でコードを直し**、そのうえで「この項目をこう解釈した／こう変えた／今の証拠はこれ」をツールに並べ直す。
7. ユーザーは次に見たときに、その解釈が正しかったかを判定する。

**このループがプロジェクトそのものです。他はすべて周辺です。**

**なぜ判定を事後にするのか。** ユーザーが**主観的な**項目を書き換えたとき、「エージェントが今それを満たしているか」の判断もまた主観的な判断であり、本プロジェクトの原則に従えば人が下すべきものです。しかし毎回止まって確認を求めれば、絶えず中断が入ります。そこでエージェントは待ちません。自分の解釈で動き、その解釈を並べ直し、人は後から判定します。この選択の代償とその手当てが設計原則 6 です。

**なぜ価値が「早さ」にあるのか。** ループ自体は最終的に「最新のリストに適合する」ところへ収束することを保証します。このツールの価値は正しさの保証ではなく、**ズレが下流の土台に広がる前に、最小の手戻りコストで人が捕まえる機会をつくること**にあります。

## 設計原則（これがこのプロジェクトの中身であり、UI の話ではない）

以下の 6 つは硬い制約です。すべての実装判断はこれらに照らして検証されます。

### 1. 意図より証拠を

エージェントに「何を検証するつもりか」だけを書かせてはいけません。意図は嘘をつけますし、検証もできません——「HIG に適合していることを確認しました」は反証不可能です。**完了と判断した根拠そのもの**を出させること。撮ったスクリーンショット、検出した色のリスト、測定したコントラスト値。

理由：人は「口に出さなかった期待を自分から思い出す」のがとても苦手で、「目の前の証拠に突かれて思い出す」のはとても得意です。色のリストに 5 色並んでいるのを見た瞬間、「白黒グレーだけのはず」という言語化されていなかった期待が**引きずり出されます**。事前に思いつく必要はありません。問題が「人が能動的に思い出す」から「証拠が受動的に引き金を引く」へ変わるのです。

### 2. 主観項目の最終判定者は人（Goodhart への防具）

ツールはエージェントを誘導して、曖昧な基準を検証可能な代理指標に分解させます。**しかし代理指標はあくまで意思疎通のための足場であって、判定者ではありません。**

- **客観項目**：エージェントが自分でチェックし、自分で通してよい。
- **主観項目**：代理指標は証拠を人の前に運ぶだけ。**エージェントが自分で「通過」と宣言することは決して許されない。**

*2026-07-29 改訂。* 元は「通過には人の承認が必要」と書かれ、実際に承認ボタンもありました。削除しました。エージェントに対して何の作用もなく（解放条件はもともと「証拠を並べた」と「承認済み」を同列に扱っていた）、また人の正直な既定値は「エージェントの仕事はまず正しいものとする」だからです。したがって主観項目に「通過」状態は存在しません。終状態は「証拠が並んでいて、人が条件を変更したか、しなかったか」です。同意は沈黙であり、行動が要るのは不同意のときだけです。

*2026-08-02 再改訂。* さらに 2 つのレバーが消えました。**差し戻し**は「この基準は残す、ただし今の証拠では通らない」を意味していました。しかし編集はすでに項目を未検証に戻し、バージョンを進め、証拠を陳腐化させ、走行中のエージェントにも届きます。一字も変えずに保存し直すだけで同じことが言えますし、そもそもエージェントが基準を読み違えたのなら、「もう一度」と言うより基準を書き直すほうが効きます。**免除**は「誰もチェックしない状態」で項目を残す仕組みでしたが、墓標が溜まっていく契約こそ原則 4 が削ろうとしている読解負荷そのものです。そこで ✕ は削除になりました——証拠ごと消えます。人に残るレバーは 2 つ、**条件を編集するか、項目を消すか**です。

代理指標によって主観項目が自動的に通ることを、決して許してはいけません。それが Goodhart の罠です——エージェントが数値を満たしにいき、「指標はすべて正しいのに全体としては変なもの」が出来上がる。この線は絶対に守ります。

この線には裏口があります。**「どれを客観とみなすか」の分類をエージェント自身に決めさせると、主観項目を客観と誤ラベルするだけで判定者を迂回できてしまいます。** よって規則は固定です。既定は必ず主観、客観には機械実行可能なオラクルが必須、人が明示的に格上げする場合はその人が責任を負う。分類の誤りは常に「人により多く見せる」側へ倒します。

### 3. 事前仕様ではなく、生きた契約

「ユーザーが最初に要件を正しく言語化できる」という前提に依存しないこと。主観的・暗黙的なものは本質的に仕様化できません——言語化できるなら人は要らないのです。リストは全過程を通じて編集可能であり、繰り返し突き合わされます。

### 4. 浮かび上がらせるものを絞る（トリアージ）

詳しく書くほど人が読む量は増える——これは本物の矛盾です。3 時間のタスクなら検証項目は数百に及びます。全部並べればユーザーは読み切れず、結果として読まなくなり、作らなかったのと同じになる。答えは「辛抱強く読んでもらう」ではなく**トリアージ**です。安全で人が見なくてよい項目はエージェントに消化させ、本当に人の判断が要る少数だけを浮かび上がらせる。

（「人の判断が要る」をどの軸で判定するかは、実データが出るまで意図的に決め打ちしません。ロードマップ参照。）

### 5. 制御の単位は「一つの目標」であり、監視は目標ごとに任意

プロジェクトとは、独立に発行される目標の連なりです。**一つの目標の実行の中では、エージェントは完了まで走り切ります——誰かを待って止まることはありません。**

つまり「見たいときだけ見る」は「実行中に人待ちのゲートを置くかどうか」ではありません。もっと単純に、**ユーザーが目標ごとに「これは横で見ていて、検証をその場で編集するか」を決める**というだけのことです。最初の 5 個は見て、次の 15 個は放置し、最後の 5 個でまた戻ってくる。目標はそれぞれ独立した発行なので、「次のから見始める」はいつでも成立し、事前に決めておく必要がありません。

### 6. 事後判定は能動的に目立たせないと、エージェントの独断と同じになる

人の判定が後から来る以上、ツールには「見るべき瞬間を見逃させない」義務が生じます。

エージェントが黙って自分の解釈で基準を読み替え、コードを直し、並べ直したとして——それが「通過」した百項目の中に埋もれ、ユーザーが「自分の意図と解釈が違う」ことに気づかなかったなら、ユーザーは**名目上**判定権を持っているだけで、実際にはエージェントが独断で決めたのと同じです。

したがってツールは、**エージェントによる主観項目の新しい解釈**を、通過項目に紛れ込ませず能動的に示さなければなりません。これは原則 4（トリアージ）と同じ仕組みです——解釈の更新こそ、まさに浮かび上がらせるべき類のものです。

## 中心にある賭け

すべてはこの一文の上に立っています。

> **「証拠」を人に見せるほうが、「文字のチェックリスト」を見せるより、言語化されていなかった自分の期待に気づかせる力が強い。**

これが偽なら、このツールは見た目のいいチェックリストにすぎません。

**判断：作る。** 想定ユーザー本人（ソフトウェアエンジニア）として、この主張は十分に確からしいと判断したため、正式な比較実験を先に走らせるのではなく「最小版を作って自分で使う」ことで検証する道を選びました。ローカルファーストで単独ユーザーのオープンソースツールにとって、「作って、自分が使い続けるかを見る」は安価で誠実な検証です。

**ただし、賭けているのがどちらの版なのかは自覚しておくこと：**

- **弱い版**（ほぼ確実に成立）：証拠を多く見せれば役に立つ。
- **強い版**（製品が実際に賭けているもの）：証拠は**言語化していなかった期待を思い出させる引き金になる**。既知の確認ではなく、抜けの発見。

弱い版が成立しても、強い版が成立するとは限りません。しかも想定ユーザー本人であることは、強い版を内側から検証する上ではむしろ不利です——自分の認知が抜けを自動的に埋めてしまうからです。だからドッグフーディングで見張るのはまさにここ。「情報が充実している」と感じたかではなく、**証拠を見たがゆえに、事前にリストへ書いていなかったものを実際に捕まえたか**です。

**だからドッグフーディングは計器付きで行い、感覚には頼りません。** 検証項目を追加・修正するたびに、ストアはその出自を記録します。(a) 実行前に書いた、(b) ある証拠を見ながら追加した（どの証拠かも記録）、(c) 実行中に自発的に思いついた。(b) の件数が強い版の直接の読み取り値です。コストはほぼゼロ——編集イベントはどのみちストアに入ります。

**作ってみて手応えがなかった場合の安価な差し戻し検証：** Wizard-of-Oz。実際のタスクを既製のエージェントで一度走らせ、その証拠を手作業でまとめ、エンジニア数名を 2 群（文字リストのみ／証拠あり）に分けて、後者のほうが事前に書かれていなかった抜けを多く捕まえるかを比べます。

## 想定ユーザー

**判断力はすでに十分にあるのに、エージェントのブラックボックスの外側に締め出されている人。** 典型的にはソフトウェアエンジニアです。

**このツールはユーザーを賢くしません。すでにある判断力に、振るう場所を与えるだけです。** 既存の認知を増幅はしますが、持っていない認知を生み出しはしません。「Apple は白黒グレーしか使わない」という概念を持たない人にいくら証拠を出しても無意味です——本人が何を見ているのか分からないからです。価値の上限はユーザー自身の認知の上限です。

**構造的にドメイン中立。** 検証される対象が美意識でも、主観的な好みでも、技術的判断（設計の妥当性、エッジケース、コードベースの慣習、セキュリティ）でも、ツールにとっては同じ動作です——エージェントに証拠を出させ、その領域の権威者につつかせる。ツールが理解しているのは**プロセスであって内容ではありません**。内容を知らないからこそ、どの領域でも使えます。「何を証拠として出すか」はエージェントが生成し、ツールは領域固有の抽出器を一切内蔵しません。

## スコープと非目標

- **ローカルファースト、単独ユーザー、オープンソース。** クラウドなし、ユーザー横断のデータ収集なし。
- **堀は狙わない。** 理解しやすく fork しやすいこと自体が機能です。
- **エージェントハーネスの代替ではない。** 「検証の透明化と協働」の層だけを担います。

**明示的にスコープ外（記録のみ）：** ユーザー横断の匿名化データから「この種のタスクでは皆が何を見落としがちか」を学習し、思いつかなかった検証項目を先回りで補う——強力な方向ですが、ローカルファースト／データを外に出さないという立ち位置と正面から衝突し、ユーザーにデータ提供の同意を求める必要もあります。

## ロードマップ

1. **最小の実用プロトタイプを作る——それ自体が検証手段。** Claude Code の hooks の上に、Stop（門番）＋ PostToolUse（配信）の対、生きた契約を読む検証コア、実行中に編集できる最小の UI。エージェントが curate した証拠と協働編集、事後判定まで。計器を付けて自分で使い込み、強い版の仮説が成立するかを見張ります。
2. エージェントが出してきた証拠をきちんと見せる。証拠を生成するのはエージェント側で、ツールは表示と印付けに徹し、領域固有の抽出器は持ちません。
3. トリアージと目標ごとの監視（任意の出入り）を追加し、原則 6 の「主観項目に対する新解釈を能動的に示す」を実装します。
4. 検証リストの形式をエージェント非依存のスキーマへ抽象化し、2 つ目の基盤エージェントを試します。
5.（条件付き）エージェント curate 型の証拠が不十分だと検証され、**かつどこが不十分かが見えた場合にのみ**、生ログ層のフィルタ規則を設計します。

## 先行事例と関連する考え方

- **Loop engineering** — 本プロジェクトの問題意識が乗っている「推論 → 行動 → 観察 → 繰り返し」の枠組み。
- **Claude Code hooks**（Stop / http / agent）— 採用している結合メカニズム。
- **[open-design](https://github.com/nexu-io/open-design)** — BYOK 統合モデルの参考。ローカルデーモン、UI、PATH を走査するエージェント別アダプタ。
- **open-codesign**（OpenCoworkAI）— その「live agent パネル：todos + tool calls + 中断可能な生成」は、「ユーザーの目の前で実行される」体験に最も近い既存実装です。
- **「A Field Guide to Fable: Finding Your Unknowns」**（Thariq Shihipar、Anthropic、2026-07）— プロンプト側から同じ問題モデルを独立に述べたもの。品質のボトルネックは自分の unknowns を明確化することにあり、そのうち **unknown knowns**（知ってはいるが言語化しておらず、結果を前にして初めて姿を現すもの）こそ、この中心仮説が収穫しようとしているものです。証拠はその現像液にあたります。

技術的な意思決定の全ログ——状態機械、武装／解除プロトコル、ターミナルデーモンの設計と、その裏にある日付入りの判断すべて——は、正典の[繁体字中国語版設計ノート](design.zh-Hant.md) にあります。

## リポジトリ構成

| パス | 中身 |
|---|---|
| `crates/witnos-core` | ドメイン型、書き込み時のルール、目標ごと 1 ファイルの JSON ストア、門番の解放条件。I/O フレームワークに依存しません |
| `crates/witnos-server` | axum コアを **lib として**提供。Tauri シェルがこれを埋め込むため、人が編集するものと門番が読むものが同一のプロセス内ストアになります。`examples/serve.rs` でヘッドレス起動も可能 |
| `crates/witnos-cli` | headless バイナリ `witnos`：両 hook（Stop 門番は fail-closed／PostToolUse 配信は fail-open）、武装／解除、エージェント向けサブコマンド、`pty-serve` ターミナルデーモン。**`tauri` crate に依存してはいけません** |
| `crates/witnos-app` | Tauri シェル。人の側は IPC、エージェントの側は HTTP——この分割は構造的な信頼境界です |
| `ui/` | webview フロントエンド（React + TypeScript、UI フレームワーク非依存、アイコンはインライン化した Lucide のパス） |
| `scripts/install-app.sh` | `/Applications/Witnos.app` への一括ビルド＆インストール |

開発コマンドは `CLAUDE.md` にあります。

## コントリビュート

まだ作者が自分で使い込んでいる段階ですが、issue と PR は歓迎します。ただし先に[設計原則](#設計原則これがこのプロジェクトの中身でありui-の話ではない)を読んでください。あの 6 つは硬い制約で、すべての実装判断がそれに照らして検証されます。とくに原則 2（エージェントは自分の主観項目を自分で通せない）と fail-closed の門番。この 2 つはツールが存在する理由そのものであり、利便性のために緩めることはありません。

方向性には賛成だが細部は別のやり方にしたい、という場合。このプロジェクトは意図的に堀を狙っていません——**理解しやすく fork しやすいことは、このプロジェクトの機能の一つです。** そのまま fork していくのも、まったく問題のない結末です。
